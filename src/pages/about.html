How I work

Understand it. Build it right. Ship it.

01

Understand the Real Problem

Before writing code I map out the actual workflow — for PesaFlow that meant understanding how Kenyans really receive and spend M-Pesa money before designing a single database table.

02

Correctness First

Money bugs are correctness bugs. I model currency as fixed-point Decimal, write validation before features, and add automated tests before anything that touches finances ships.

03

Ship, Then Iterate

I favor small, deployed, working versions over big-bang rewrites. I keep a running log of what's actually shipped versus what's claimed — and correct the record when they drift.

Hardened by default

Practices I Don't Compromise On

I maintain a personal security-hardening standard, aligned with OWASP Top 10, that I run at the start of every serious project — not because a client asked, but because it's how I think software should be built.

Decimal Money, Never Float

Every amount in a financial system I build is a fixed-point Decimal. Floats drift, and drift in money is a bug, not a rounding error.

Append-Only Audit Logs

Where a record of what happened matters, the audit log is enforced append-only at the database grant level — not just in application code that could be bypassed.

Server-Side Role Verification

A user's role is re-checked from the database on every authenticated request. A token claim is never trusted on its own.

Input Validation & Sanitisation

Every input is validated with a schema (Zod) and sanitised before use — blocking injection and XSS at the source, not after the fact.

CSP & Security Headers

A strict Content Security Policy and subresource integrity hashes on every external script — not just SSL and a privacy policy.

Rate Limiting

Forms and auth endpoints are rate-limited by default — stops credential stuffing and spam before it becomes a problem.
